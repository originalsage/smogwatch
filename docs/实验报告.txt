================================================================================
                        雾霾探测系统（SMOGWATCH）实验报告
================================================================================

摘要
----
本实验围绕雾霾与出行健康需求，设计并实现了一套手机端雾霾探测系统。系统采用
Spring Boot 作为后端服务，UniApp 作为跨端前端，结合百度地图开放平台提供的
定位与天气能力，实现城市定位在服务器端的持久化、实时天气与空气质量指数的
动态展示，以及未来 24 小时温湿度趋势与逐小时明细。本文从问题背景、总体方案、
数据链路、运行结果与体会五个方面进行阐述。

--------------------------------------------------------------------------------
一、问题描述
--------------------------------------------------------------------------------

1.1 现实背景
雾霾等大气污染现象频发，直接影响公众出行安排与身体健康。出行前若能获知
所在或目标城市的空气质量与气象条件，有助于采取佩戴口罩、减少户外活动、
调整出行时段等防护措施，从而降低不利气象与污染因子的综合影响。

1.2 任务目标
根据课程与项目要求，需在移动端完成“雾霾探测”类应用，核心目标包括：
（1）定位功能：获取用户所在或选定城市，将定位/选定的城市信息保存于服务
    器端，并在客户端界面同步展示；
（2）界面设计：以适配手机屏幕的布局呈现天气与空气质量指数，支持数据
    的动态刷新与分层展示；
（3）天气详情与空气质量：在服务器端依据城市信息调用第三方天气接口
    （本实现采用百度天气相关接口），获取并解析天气详情与空气质量数据，
    将关键结果持久化后供前端详情页与图表使用；
（4）文档与报告：对问题、方案、数据获取、结果与心得进行系统总结。

1.3 待解决的关键问题
如何在异构终端上保持界面一致性；如何在后端统一鉴权、限流与容错地调用
外部 API；如何将“定位—行政区—天气/空气质量—缓存或落库—前端展示”
整条链路贯通并便于维护。


--------------------------------------------------------------------------------
二、方案设计
--------------------------------------------------------------------------------

2.1 总体架构
系统采用经典的前后端分离架构：
- 前端：UniApp 开发，编译为各端小程序或 H5，负责定位授权与展示、路由
  跳转、图表与列表渲染；
- 后端：Spring Boot 提供 RESTful 接口，封装对百度地图开放平台（IP 定位、
  天气服务等）的访问，并完成业务校验、异常处理与数据持久化；
- 数据层：关系型数据库（MySQL）存储城市定位记录、天气快照等结构化数据，
  便于审计与历史查询（具体表结构以实现为准）。

2.2 功能模块划分
（1）定位与城市模块：解析客户端或网关传递的位置上下文，结合百度 IP 定位
    或用户手动选择的城市/区县，生成标准化的省市区展示文案，并写入服务
    器端；
（2）天气与空气质量模块：根据行政区编码或城市维度请求百度天气接口，
    聚合实时天气、AQI、PM2.5 以及未来 24 小时逐小时预报；
（3）配置与容错模块：对外部 HTTP 调用设置超时与重试策略，统一异常返回
    格式，避免前端直接暴露第三方接口细节；
（4）跨域与安全：后端配置 CORS 策略以支持 H5/开发联调；敏感配置项
    （如 AK、数据库口令）集中于 application 配置，不硬编码于业务类中。

2.3 界面与交互设计（对应截图中的实现要点）
（1）首页（雾霾探测）：顶部品牌与标题区；中部“当前城市”卡片展示服务
    器确认后的行政区全称；Body 区域分为“实时天气”栅格（温度、体感、
    湿度、风力、风向等）与“空气质量”卡片（AQI 数值、等级、色带刻度、
    健康提示、PM2.5 浓度）；提供“详情与曲线”入口跳转至天气详情页；
（2）天气详情页：展示“未来 24 小时预报”说明、温湿度双折线图及图例、
    数据来源标注（百度未来 24 小时逐小时预报）、温湿度区间摘要，以及
    “逐小时明细”列表（时间戳、温度、湿度、天气现象文字）。

2.4 技术选型理由
- Spring Boot：生态成熟，便于快速集成 Web、JDBC/MyBatis 与 HTTP 客户端；
- UniApp：一次开发多端发布，利于解决不同机型分辨率下的布局适配问题；
- 百度地图开放平台：与任务说明中“百度地图 API 获取定位与天气”的要求一致，
  接口文档相对集中，便于联调。


--------------------------------------------------------------------------------
三、数据获取
--------------------------------------------------------------------------------

3.1 定位数据
依据项目说明，定位数据可通过百度地图相关接口获取。本系统后端配置了百度
地图 IP 定位等接口地址，由服务端发起 HTTPS 请求，解析返回 JSON 中的省、
市、区（县）及 adcode 等字段，用于界面展示与后续天气查询的键值关联。
客户端在获得授权或网络环境允许的前提下，将定位结果或手动选择结果提交
后端，由后端统一落库或更新会话维度的城市记录，实现“服务器保存、客户端
展示”的一致性。

3.2 天气与空气质量数据
天气详情与空气质量指数由后端调用百度天气服务（如 weather/v1 等版本化路径）
获取。请求参数通常包括服务端持有的访问密钥（AK）、经纬度或行政区编码等。
返回体中包含实时天气现象、温度、湿度、风力风向、AQI、首要污染物及逐小时
预报数组等字段。后端对响应进行 DTO 映射与必要字段校验后，将关键快照写入
数据库（如天气快照、城市定位日志等实体），前端通过自有 REST 接口拉取，
避免浏览器直连第三方接口带来的密钥泄露与跨域复杂问题。

3.3 行政区与编码辅助
项目中通过内置或资源文件形式的行政区编码表（如 CSV）辅助将展示名称与
第三方接口所需的 district_id / adcode 对齐，减少手工维护成本并降低
“有定位无天气”的匹配失败率。

3.4 可靠性与工程实践
对外部 API 设置合理超时与有限次重试；对解析失败、HTTP 非 200、业务码
异常等情况统一转换为应用内错误码与提示文案；数据库连接使用独立配置
与时区参数（如 Asia/Shanghai），保证时间戳展示与业务日一致。


--------------------------------------------------------------------------------
四、结果展示及分析
--------------------------------------------------------------------------------

4.1 部署与联调结果
系统已完成部署。首页可正确显示当前城市为“陕西省西安市雁塔区”等完整
行政区名称，证明定位或选定城市信息已由服务端确认并回传前端展示。

4.2 实时天气与空气质量
首页“实时天气”区域展示现象（如晴）、温度与体感温度、湿度、风力等级
与风向等，满足任务对“Body 部分天气动态显示”的要求。“空气质量”区域
以醒目数值与等级（如优）及色带形式展示 AQI，并给出健康提示与 PM2.5 浓度，
符合“空气质量指数动态显示”的要求。

4.3 天气详情与曲线
在“详情与曲线”页面中，折线图同时绘制温度（℃）与湿度（%）随时间变化
趋势，横轴为小时刻度，图例区分两条曲线；页面注明数据来源于百度未来
24 小时逐小时预报，与任务书指定的数据渠道一致。图下给出温度、湿度区间
摘要，列表区给出逐小时时间戳、温度、湿度及天气文字（如多云），便于用户
从“趋势 + 明细”两个粒度理解未来环境变化。

4.4 简要分析（结合示例数据）
以截图所示时段为例：午后至傍晚温度较高（如约 32℃），湿度相对较低，
天气现象以晴或多云为主，AQI 处于优良区间，提示适宜户外活动。从产品设计
角度，用户在出行前可同时参考“当前污染水平”与“未来温湿度走势”，对
是否长时间户外、是否补水防晒等具有辅助决策价值。若遇高污染或剧烈温湿
度波动，同一套界面结构仍可承载警示性文案与色阶变化，扩展性良好。


--------------------------------------------------------------------------------
五、心得与体会
--------------------------------------------------------------------------------

5.1 工程层面
前后端分离后，接口契约（路径、字段、错误码）成为协作核心。将第三方
天气与定位全部收敛到 Spring Boot，有利于密钥管理、日志审计与后续替换
供应商（如说明中提到的和风、墨迹等）时仅改适配层。

5.2 数据与体验
外部 API 存在配额、延迟与偶发故障，必须在产品层给用户明确反馈（加载中、
重试、降级文案），在实现层用超时、重试与落库快照减轻瞬时失败对体验的
冲击。图表与列表双呈现能兼顾“一眼看趋势”和“精确到小时”的需求。

5.3 移动端适配
采用 UniApp 与卡片化布局，可在不同像素密度下保持相对稳定的留白与字号
层次；折线图组件的引入使抽象数字转化为可感知曲线，符合课程对 HTML5/
移动端适配与可视化的导向。

5.4 总结
本实验完成了从需求分析、接口选型、后端聚合与持久化、到前端可视化与
详情页的闭环。既满足了课程对定位、天气、空气质量与实验报告的要求，
也为后续增加历史对比、预警推送或多数据源融合预留了架构空间。
